# 블로그 초안 작성

요청: $ARGUMENTS

## 1. 인자 해석

- 끝에 붙은 플랫폼·유형 단어를 떼어 내고, 나머지를 키워드로 본다. 순서는 상관없다.
  - 플랫폼: `티스토리`·`tistory` → `tistory`, `블로거`·`blogger`·`구글` → `blogger`, `네이버`·`naver` → `naver`. 없으면 `tistory`
  - 유형: `정보`·`info` → `info`, `리뷰`·`후기`·`review` → `review`, `장소`·`맛집`·`여행`·`place` → `place`. 없으면 키워드를 보고 판단한다 (상품·서비스 사용기면 `review`, 맛집·카페·여행지·시설 방문기면 `place`, 그 밖에는 `info`)
  - 구성: `구성A`~`구성D` 또는 `A형`~`D형`이 있으면 그 구성. 없으면 지정하지 않는다 (브리프가 무작위로 골라 글마다 구조가 달라지게 한다)
- 키워드가 여러 개면 키워드마다 브리프를 따로 받으므로 구성도 각각 다르게 골라진다. 같은 구성을 억지로 맞추지 않는다.
- 키워드가 쉼표로 여러 개면 키워드마다 아래 2~6단계를 반복한다.
- 키워드가 없으면 작성하지 말고 사용법(`/blog-draft <키워드> [플랫폼]`)을 안내한다.

## 2. 이미 쓴 초안 확인

- `drafts/`에서 같은 키워드(파일 이름의 키워드 부분, 공백은 하이픈)로 쓴 초안이 있는지 본다. 있으면 작성은 계속하되, 마지막 보고에 "같은 키워드의 초안이 이미 있음"과 파일 이름을 알린다.
- 최근 초안 5개 정도의 추천 제목과 본문 첫 문장을 훑어보고, 이번 글은 **같은 제목 패턴·같은 첫 문장 방식을 피한다.**

## 3. 브리프 조회

저장소 루트에서 실행한다.

```bash
npm run --silent brief -- "<키워드>" --platform <플랫폼> --type <유형> [--structure <A~D>]
```

출력된 `[글쓰기 브리프]`가 이번 작업의 입력이다. 키가 없다는 안내(검색광고·API HUB)가 나오면 있는 정보만으로 진행하고, 마지막 보고에 그 사실을 알린다.

**연관어로 돌리기**: 브리프에 `경쟁 판단`과 `추천 타깃 키워드`가 있으면 대표 키워드로 바로 쓰지 않는다 (문서가 수만~수십만 개라 상위에 오르지 못함).

- `writing.md`의 "메인 키워드 정하기"대로 포화도 `기회`이면서 글로 답할 수 있는 타깃 키워드 하나를 고른다.
- 고른 키워드로 위 명령을 다시 실행해 그 브리프로 쓴다. 이후 단계의 "키워드"(파일 이름 포함)는 고른 키워드다.
- 사용자가 키워드를 그대로 쓰라고 했으면(예: "그대로", "대표 키워드로") 돌리지 않는다.
- 연관어도 모두 경쟁이 세다고 나오면 원래 키워드로 쓰되 제목을 구체적으로 좁히고, 보고에 알린다.

## 4. 규칙 읽기

아래 파일을 모두 읽고, claude.ai 프로젝트에 브리프를 붙여넣었을 때와 똑같이 따른다.

- `docs/prompts/project-instructions.md` (역할, 내 블로그 정보, 공통 원칙)
- `docs/prompts/writing.md` (브리프 항목 쓰는 법, 작성 순서, 사람이 채울 자리, 출력 형식)
- `docs/prompts/types/<유형>.md` (구성 변형 A~D, 이미지·직접 작성 자리 기준) — 브리프의 `구성:` 변형을 따른다
- `docs/prompts/platforms/<플랫폼>.md`
- `docs/prompts/threads.md`

"내 블로그 정보"가 `[예: …]` 그대로 채워지지 않았으면 예시 값을 기준으로 쓰고, 마지막 보고에 채워 달라고 안내한다.

## 5. 사실 확인과 작성

- 제도·금액·날짜·수치는 웹 검색으로 최신 정보를 확인하고, 공식 출처를 우선한다. 확인하지 못한 내용은 본문에서 빼거나 확인할 곳을 알려 주는 문장으로 쓰고 "사람이 할 일"에 적는다. 본문에 남기는 표시는 `[이미지: …]`뿐이다 (`[직접 작성]`·`[확인 필요]`는 쓰지 않는다).
- `writing.md`의 출력 형식(제목 후보 → 메타 설명 → 태그 → 본문 → 이미지 목록 → 사람이 할 일 → 참고한 출처 → 스레드 홍보글) 순서를 그대로 지킨다.
- 저장하기 전에 `writing.md` 작성 순서 6번(내보내기 전 확인)대로 제목 글자 수·메인 키워드 횟수·남은 표시를 확인한다. 분량은 플랫폼 규칙의 **목표**(네이버 2,000자)와 소제목별 배분에 맞춰 쓴다 (범위의 최소에 맞추지 않는다).

## 6. 파일 저장

- 경로: `drafts/<오늘 날짜 YYYY-MM-DD>-<키워드의 공백을 하이픈으로 바꾼 것>-<플랫폼>.md`
  - 예: `drafts/2026-10-29-국민연금-수령나이-tistory.md`
- 같은 파일이 있으면 덮어쓰지 말고 끝에 `-2`, `-3`을 붙인다.
- 저장한 뒤 `npm run --silent draft-length -- <저장한 파일>`로 본문 글자 수를 잰다. 목표보다 짧다고 나오면 안내대로 보완해 같은 파일에 다시 쓰고, "분량 맞음"이 나올 때까지 반복한다 (눈대중으로 세지 않는다).
- 파일 맨 위에는 사용한 브리프를 접어 둔다.

  ```markdown
  <details><summary>글쓰기 브리프</summary>

  (3단계 출력 그대로)

  </details>
  ```

## 7. 보고

초안 전체를 대화창에 다시 출력하지 않는다. 키워드마다 아래만 짧게 보고한다.

- 저장한 파일 경로
- 연관어로 돌렸으면 `원래 키워드 → 고른 키워드`와 이유 한 줄 (검색량·문서 수)
- 추천 제목, 글 유형, 구성
- 웹에서 보려면 toolhub 웹의 초안 메뉴(`/drafts`)에서 열 수 있다는 안내
- 본문 글자 수 (`draft-length` 결과 그대로)
- 이미지 자리: 대표 썸네일 1개(`[이미지: 대표 썸네일 | alt: … | 추천: 썸네일 만들기]`, 장면 없음) + 본문 5개인지 (사용기·방문기가 아니면 본문 이미지가 모두 `추천: AI 생성` 장면인지 확인)
- 확인하지 못해 빼거나 돌려 쓴 내용이 있으면 한 줄씩
